# 需求：用户名 + 邮箱登录注册 + GitHub 用户查询 + 人员管理

## 1. 背景与目标

做一个最基础的可用版本：

1. 用户注册时填写 **用户名、邮箱和密码**；登录时可以用 **用户名或邮箱** 加密码。
2. 登录后进入一个页面，输入 GitHub 用户名就能查到这个人的公开资料。

本期只做 **Web 端**（`apps/web`），后端改动在 `apps/server` 和 `packages/*`。移动端（`apps/native`）放到后续迭代。

## 2. 范围

| 本期做 | 本期不做 |
| --- | --- |
| 用户名 + 邮箱 + 密码注册 | 邮箱验证、找回 / 重置密码 |
| 用户名或邮箱 + 密码登录、退出登录 | 第三方登录（GitHub OAuth 等） |
| 未登录访问受保护页面时跳转到登录页 | 修改用户名、邮箱或密码，个人资料编辑 |
| 按 GitHub 用户名查询公开资料 | 查询历史、收藏、仓库列表详情 |
| 人员入库（新增）、列表查询、修改、删除（R4，第二期） | 人员批量导入 / 导出、操作日志、角色权限、软删除与回收站 |
| | 移动端（`apps/native`）适配 |

## 3. 功能需求

### R1 注册

**页面**：`/login`（与登录在同一页，可切换“登录 / 注册”）

**表单字段**：

| 字段 | 规则 |
| --- | --- |
| 用户名 | 必填，3–30 位，只允许字母、数字、下划线 `_` 和点 `.`；不区分大小写（`Tom` 和 `tom` 视为同一个） |
| 邮箱 | 必填，合法邮箱格式；不区分大小写；不需要验证 |
| 密码 | 必填，8–128 位 |
| 确认密码 | 必填，必须与密码一致 |

**行为**：

- 前端实时校验，不合法时在对应字段下方显示错误提示；提交按钮在请求过程中显示加载状态，并禁止重复提交。
- 用户名已被占用时提示“用户名已存在”，邮箱已被注册时提示“邮箱已被注册”。
- 注册成功后自动登录，跳转到 `/dashboard`。

**验收标准**：

- [ ] 输入 `ab`、`a b`、`中文名` 等不合法用户名时无法提交，并显示原因
- [ ] 输入 `abc`、`a@b` 等不合法邮箱时无法提交，并显示原因
- [ ] 两次密码不一致时无法提交
- [ ] 用已存在的用户名注册（包括只是大小写不同），提示“用户名已存在”
- [ ] 用已注册的邮箱注册，提示“邮箱已被注册”
- [ ] 注册成功后直接进入 `/dashboard`，刷新页面后仍保持登录状态

### R2 登录 / 退出

**表单字段**：

| 字段 | 规则 |
| --- | --- |
| 用户名或邮箱 | 必填。输入中包含 `@` 时按邮箱登录，否则按用户名登录 |
| 密码 | 必填 |

**行为**：

- 账号或密码错误时统一提示“账号或密码错误”，不透露具体是哪一项错。
- 登录成功跳转到 `/dashboard`。
- 已登录用户访问 `/login` 时直接跳转到 `/dashboard`。
- 顶部导航的用户菜单显示当前用户名和邮箱，并提供“退出登录”；退出后回到 `/login`。

**验收标准**：

- [ ] 用户名 + 密码可以登录，用户名大小写不同也能登录
- [ ] 邮箱 + 密码可以登录，邮箱大小写不同也能登录
- [ ] 错误密码、不存在的账号都显示同一句错误提示
- [ ] 已登录时访问 `/login` 会被重定向到 `/dashboard`
- [ ] 退出后访问 `/dashboard` 会被重定向到 `/login`

### R3 GitHub 用户查询

**页面**：`/dashboard`（仅登录用户可访问，未登录重定向到 `/login`）

**交互**：

1. 页面上有一个搜索框和“搜索”按钮，按回车也能搜索。
2. 输入为空时不发请求。
3. 搜索中显示加载状态（骨架屏或 loading）。
4. 查询成功后以卡片形式展示资料。

**展示字段**（来自 GitHub 公开 API `GET https://api.github.com/users/{username}`）：

| 字段 | GitHub 字段 | 说明 |
| --- | --- | --- |
| 头像 | `avatar_url` | |
| 昵称 | `name` | 为空时显示用户名 |
| 用户名 | `login` | 点击跳转到 GitHub 主页（`html_url`），新窗口打开 |
| 简介 | `bio` | 为空时不显示该行 |
| 公司 | `company` | 为空时不显示 |
| 所在地 | `location` | 为空时不显示 |
| 博客 / 网站 | `blog` | 为空时不显示；可点击，新窗口打开 |
| 公开仓库数 | `public_repos` | |
| 粉丝数 / 关注数 | `followers` / `following` | |
| 注册时间 | `created_at` | 格式化为 `YYYY-MM-DD` |

**异常处理**：

| 场景 | 提示 |
| --- | --- |
| 用户名格式不合法（GitHub 规则：1–39 位，字母数字或中间单个连字符 `-`，不能以 `-` 开头或结尾） | 前端直接提示“GitHub 用户名格式不正确”，不发请求 |
| 用户不存在（GitHub 返回 404） | “未找到该 GitHub 用户” |
| 请求频率超限（GitHub 返回 403 / 429） | “请求过于频繁，请稍后再试” |
| 网络错误或其他错误 | “查询失败，请稍后再试” |

**验收标准**：

- [ ] 搜索 `torvalds` 能显示头像、昵称、仓库数、粉丝数等信息
- [ ] 搜索一个不存在的用户名，显示“未找到该 GitHub 用户”，页面不崩溃
- [ ] 输入 `-abc` 或超过 39 位的字符串，前端直接提示格式错误，没有发出网络请求
- [ ] 字段为空（如没有 `bio`）时对应行不显示，不出现 `null` 或 `undefined`
- [ ] 外部链接带有 `target="_blank"` 和 `rel="noopener noreferrer"`
- [ ] 5 分钟内重复搜索同一个用户名时命中缓存，不重复请求

### R4 人员管理（入库、修改、删除）

> 第二期新增（2026-11-07）。“人员”是独立的业务数据，与登录账号（`user` 表）无关联；所有登录用户都可以管理全部人员，本期不区分角色权限。

**页面**（都只允许登录用户访问，未登录重定向到 `/login`）：

| 页面 | 路径 | 说明 |
| --- | --- | --- |
| 人员列表 | `/persons` | 顶部导航新增“人员管理”入口 |
| 新增人员 | `/persons/new` | 列表页“新增人员”按钮进入 |
| 编辑人员 | `/persons/[id]/edit` | 列表每行的“编辑”按钮进入 |

**人员字段**：

| 字段 | 规则 |
| --- | --- |
| 姓名 | 必填，去掉首尾空格后 1–50 个字符 |
| 工号 | 必填，2–32 位，只允许字母、数字和连字符 `-`；统一转大写存储；**全局唯一**（不区分大小写，`a001` 和 `A001` 视为同一个） |
| 手机号 | 选填，中国大陆 11 位手机号（`1` 开头，第二位 3–9） |
| 邮箱 | 选填，合法邮箱格式，统一转小写存储；不要求唯一 |
| 部门 | 选填，最多 50 个字符 |
| 职位 | 选填，最多 50 个字符 |
| 状态 | 必填，“在职” / “离职”，新增时默认“在职” |
| 备注 | 选填，最多 500 个字符 |
| 创建时间 / 更新时间 | 系统自动记录，列表显示更新时间，格式 `YYYY-MM-DD HH:mm` |

选填字段留空时存为空值（`null`），不存空字符串。

**列表**：

- 表格列：工号、姓名、部门、职位、手机号、状态、更新时间、操作（编辑 / 删除）。
- 按更新时间倒序，每页 20 条，提供上一页 / 下一页和“第 X / Y 页，共 N 条”。
- 搜索框按 **姓名或工号** 模糊搜索（不区分大小写），按回车或点击“搜索”生效，搜索后回到第 1 页；状态可筛选“全部 / 在职 / 离职”。
- 没有数据时显示空状态“暂无人员”，并引导点击“新增人员”；搜索无结果时显示“没有找到匹配的人员”。
- 空字段在表格里显示 `-`，不出现 `null` / `undefined`。

**新增 / 编辑**：

- 新增和编辑共用一个表单；编辑页打开时回填当前数据。
- 前端实时校验，不合法时在字段下方显示原因；提交中按钮显示加载状态并禁止重复提交。
- 工号已被占用时，在工号字段下提示“工号已存在”。
- 保存成功后 toast 提示“已保存”，返回列表页并能看到最新数据。
- 编辑一个已被删除的人员（打开编辑页或提交时）提示“该人员不存在或已被删除”，并提供返回列表的入口。
- 提供“取消”按钮返回列表，不保存。

**删除**：

- 点击“删除”弹出确认对话框：“确定删除人员「姓名（工号）」吗？删除后无法恢复。”，确认后才删除。
- 本期为 **物理删除**；删除成功后 toast 提示“已删除”并刷新列表（当前页删空时自动回到上一页）。
- 删除一个已经不存在的人员时提示“该人员不存在或已被删除”，并刷新列表。

**验收标准**：

- [ ] 未登录访问 `/persons`、`/persons/new`、`/persons/xxx/edit` 都重定向到 `/login`；未登录调用人员相关接口返回 `UNAUTHORIZED`
- [ ] 顶部导航有“人员管理”入口
- [ ] 填写必填项即可新增成功，新人员出现在列表第一行；选填项留空时列表显示 `-`
- [ ] 姓名为空、工号含中文或空格、手机号不是 11 位、邮箱格式不对时无法提交，并显示原因
- [ ] 用已存在的工号新增或把别人的工号改成自己的（包括只是大小写不同），提示“工号已存在”
- [ ] 编辑后保存，列表显示修改后的数据，更新时间变化
- [ ] 删除需要二次确认；取消不删除；确认后该人员从列表消失，刷新后也不存在
- [ ] 按姓名或工号的一部分可以搜到人员；状态筛选生效；超过 20 条时可以翻页
- [ ] 编辑或删除一个已被删除的人员时显示“该人员不存在或已被删除”，页面不崩溃
- [ ] 列表、表单、确认对话框只用键盘就能完成操作；在亮色 / 暗色主题下正常显示；在 375px 宽的屏幕上不出现页面级横向滚动（表格可以在自身容器内横向滚动）

## 4. 技术方案约束

基于现有架构（详见根目录 `AGENTS.md`）：

### 认证

- 在 `packages/auth` 中启用 Better Auth 的 **`username` 插件**，Web 客户端加 `usernameClient()`。保留现有的 `emailAndPassword`，不开启 `requireEmailVerification`。
- 注册：调用 `authClient.signUp.email({ email, password, username, name })`，`name` 是 Better Auth 的必填字段，直接用用户名填充。
- 登录：输入包含 `@` 时调用 `signIn.email`，否则调用 `signIn.username`。
- 用户名唯一性和格式由插件校验（默认 3–30 位，字母、数字、`_`、`.`，统一转小写存储），前端用相同规则做提前校验。
- 改完插件配置后执行 `pnpm run auth:generate` 重新生成 `auth.prisma`（会新增 `username`、`displayUsername` 字段），再执行 `pnpm run db:migrate`。

### GitHub 查询

- 由 **后端代理** 请求 GitHub，前端不直接调用 GitHub API：
  - 在 `packages/api/src/routers/` 下新增 `github` 子路由，提供 `github.getUser`，使用 `protectedProcedure`（只有登录用户能调用），入参用 Zod 校验 GitHub 用户名格式。
  - 服务端只返回第 3 节表格中需要的字段，不把 GitHub 原始响应整体透传。
  - 把 GitHub 的 404、403/429 映射成对应的 `TRPCError`（如 `NOT_FOUND`、`TOO_MANY_REQUESTS`），前端根据错误码显示文案。
  - 请求头带 `Accept: application/vnd.github+json` 和 `User-Agent`。
- 未认证调用 GitHub API 时，每个 IP 每小时限 60 次。预留可选环境变量 `GITHUB_TOKEN`（在 `apps/server/.env.schema` 中声明为可选、敏感），配置后以 `Authorization: Bearer` 方式调用，额度提升到每小时 5000 次。
- 前端用 `useTRPC()` + TanStack Query 调用，`staleTime` 设为 5 分钟。

### UI

- 使用 `packages/ui` 中已有的 shadcn 组件（`Card`、`Input`、`Button`、`Skeleton` 等），缺少的组件（如 `Avatar`）通过 `npx shadcn@latest add avatar -c packages/ui` 添加。
- 表单沿用 TanStack Form + Zod。

### 人员管理

- **数据表**：在 `packages/db/prisma/schema/` 新建 `person.prisma`，模型 `Person`（`@@map("person")`），字段对应 R4 表格；`id` 用 `String @id @default(cuid())`，`employeeNo` 加 `@unique`，状态用 Prisma `enum PersonStatus { ACTIVE INACTIVE }`；`createdAt` / `updatedAt` 自动维护。为列表查询给 `updatedAt` 加索引。执行 `pnpm run db:generate`，再 `pnpm run db:migrate -- --name add_person`（非交互环境必须带 `--name`）。E2E 的 `global-setup` 清空业务表时要包含 `person` 表。
- **API**：在 `packages/api/src/routers/` 新增 `person` 子路由并合并进 `appRouter`，全部使用 `protectedProcedure`，入参用 Zod 校验：
  - `person.list({ keyword?, status?, page, pageSize })` → `{ items, total, page, pageSize }`，`pageSize` 上限 100；
  - `person.getById({ id })`、`person.create(input)`、`person.update({ id, ...input })`、`person.delete({ id })`。
  - 工号唯一冲突（Prisma `P2002`）映射为 `TRPCError` `CONFLICT`；记录不存在（`P2025` 或查不到）映射为 `NOT_FOUND`；前端按错误码显示文案。
  - 服务端统一做 trim、工号转大写、邮箱转小写、空字符串转 `null`，不信任前端。
- **前端**：列表、表单用 `useTRPC()` + TanStack Query；新增 / 修改 / 删除成功后让 `person.list` 相关查询失效（`invalidateQueries`）。表单沿用 TanStack Form + Zod，前端校验规则与后端保持一致。`/persons` 系列页面沿用 `dashboard/page.tsx` 的服务端 session 校验方式。
- **UI**：使用 `packages/ui` 已有组件；缺少的 `table`、`alert-dialog`、`select`（或 `radio-group`）、`pagination` 等通过 `npx shadcn@latest add <组件> -c packages/ui` 添加。
- **测试**：Zod 校验与数据归一化写单元测试；`person` 路由写集成测试（覆盖未登录、冲突、不存在等错误码）；Playwright E2E 覆盖新增、搜索、翻页、编辑、删除和工号冲突。

## 5. 非功能需求

- 密码由 Better Auth 负责哈希存储，不得明文记录或打印到日志。
- 所有页面支持亮色 / 暗色主题，在 375px 宽的手机屏幕上不出现横向滚动。
- 表单输入框都有对应的 `<label>`，可以只用键盘完成注册、登录、搜索和人员的增删改查。
- 提交前通过 `pnpm run check` 和 `pnpm run check-types`。
